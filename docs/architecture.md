# Nemo：Spring Cloud → Go 迁移架构方案

> 状态：评审稿 v2.2
> 日期：2026-09-04
> 范围：20 个后端服务的整体重构架构、技术选型、项目边界、部署与迁移方案
> 本版取代 v2.1。与 v2.1 的差异见附录 B（决策变更记录）。

---

## 1. 背景与目标

现有系统为 Spring Cloud 体系，约 20 个后端服务，注册中心 ZooKeeper，部署形态为虚拟机 + Docker（无 K8s）。

重构目标：

| # | 目标 | 本方案对应决策 |
|---|------|--------------|
| 1 | 网关层同时支持普通 API 调用与 AI agent 调用 | **自研 Go 网关服务**（go-zero 实现）：普通 API 反代 + AI 能力内置为可拆模块（§4） |
| 2 | 引入成熟微服务框架 | **go-zero**：api 服务 + goctl 生成骨架 + 框架级超时/熔断/限流/日志/指标默认值（§3.2） |
| 3 | 项目边界与职责清晰，多人并行开发不易冲突 | Monorepo + 独立 go module + 编译器/CI 强制依赖规则 |
| 4 | 登录对接已有统一认证 | **CAS 协议**：Web 登录走 CAS，程序化调用走 API key（§4.2） |

补充约束（2026-09 评审确认）：

- 保留现有服务的拆分粒度
- **双轨并行**：Java 栈与 Go 栈各自独立成体系、入口不同（Nginx 按 path 分流）；Go 栈稳定运行一段时间后，Java 体系直接下线
- 部署环境：虚拟机 + Docker Compose，不引入 K8s
- 业务形态：常规 CRUD 为主 + agent 流量（**主要直连外部 LLM**，少量自有 agent 服务）
- 前端为**两个独立应用**（对内一个、业务一个），各自独立仓库，基座架构相同（§8）

### 1.3 为什么继续使用微服务架构

保留现有服务的拆分粒度。理由：

- **崩溃隔离**：单体里 panic 可被 recovery 中间件兜住，但内存泄漏、fd 泄漏、CGO 段错误会让整个进程带着全部业务一起死；微服务只死一个域。
- **部署隔离**：单体任何一行代码上线都要重启整个进程，正在运行的长任务（AI agent 流式调用，分钟级）全部断连；微服务只重启自己。
- **资源隔离**：单个接口打满 CPU/内存时，单体拖慢所有接口；拆分后各服务受独立的资源配额与限流保护。
- **依赖污染隔离**：引入带漏洞或行为异常的第三方库，影响面是单个服务而非全部代码。

## 2. 总体架构

双轨并行模型：Java 栈与 Go 栈**各自独立成体系、入口不同**，由 Nginx 按 path 分流同时承载线上流量；Java 栈进入冻结状态（只修缺陷，不做新需求），新需求全部落在 Go 栈。Go 栈整体稳定运行一段时间后，Java 体系**直接下线**。

```
                 客户端 / AI Agent / 第三方
                           │
                Nginx（现有接入层，保留不动）
            ┌──────────────┴───────────────┐
            │ 按 path 分流双栈               │
            ▼                               ▼
┌──────────────────────┐        ┌──────────────────────────────┐
│  Java 栈（存量，冻结）  │        │  Go 栈（新建）                 │
│  Spring Cloud GW      │        │  自研网关 gateway ×2（go-zero） │
│  服务 × 20            │        │   ├─ 普通 API ──► 反代         │
│  （ZooKeeper 注册）    │        │   ├─ /llm/* ─► 网关内 AI 模块 ─► 外部 LLM
└──────────────────────┘        │   └─ /agent/* ► agent 服务     │
                                │   服务 × 20（注册中心注册）      │
                                └──────────┬───────────────────┘
                                           │
              共享数据层：MySQL / Redis / MQ（双栈共用，不迁移）
              新增：注册中心集群（Consul 或 etcd，§3.3）/ Prometheus + Grafana
              Java 下线后退役：ZooKeeper、Spring Cloud GW
```

要点：

- **入口隔离是并行的前提**：两栈各有完整的网关入口与注册中心，互不依赖对方设施。切流动作全部发生在 Nginx 的 path 规则上；回退 = 把 path 切回 Java 入口，分钟级完成。双轨期 Java 栈保持完整可承载全量的回退能力。
- **网关是自研的 Go 服务**（go-zero api 服务，双实例）：普通 API 反代、认证验证、限流、AI 直连流量代理全部收在它身上（§4）。它与其他服务同构——注册到注册中心、复用统一发布与监控体系；AI 能力以**进程内可拆模块**承载（§4.4）。
- **数据库是共享层而非迁移对象**：同一时刻一条业务路径只由一个栈承载（path 级分流），不存在双写；Go 服务直接接管现有库。
- **注册中心选型待定**（Consul vs etcd，§3.3）：go-zero 原生融合度与运维能力的权衡，实施阶段 0 定稿；两侧接入均做成可切换抽象。

## 3. 技术选型

### 3.1 选型总表

| 关注点 | 选型 | 替代的 Spring Cloud 组件 |
|--------|------|--------------------------|
| 边缘网关 | **自研 go-zero 网关服务**（标准库 `httputil.ReverseProxy` 转发内核；AI 能力内置模块，见 §4） | Spring Cloud Gateway |
| **注册中心** | **待定：Consul 或 etcd**（Go 栈专用，见 §3.3） | ZooKeeper（Java 栈继续用，下线后退役） |
| 认证 | CAS（对接已有服务端）+ 平台 JWT（HS256）+ API key，authz 服务承载（8084；2026-09-21 起 auth 链路并入 authz，§4.2） | Spring Security |
| 授权 | **ReBAC**（关系型访问控制）：OpenFGA 引擎以 Go module 嵌入 services/authz，设计见 `permission-design.md` | - |
| 服务框架 | **go-zero**（api 服务 + goctl 生成骨架，见 §3.2） | Spring Boot starter 全家桶 |
| 熔断 / 限流 | go-zero 内置（breaker / load shedding）+ 网关请求级限流 | Hystrix / Resilience4j |
| 配置 | go-zero config（yaml + 环境变量覆盖），无配置中心客户端 | Config Server / @Value |
| 日志 | go-zero logx（kit 统一字段约定与轮转初始化，见 §5 / §9.2） | starter-logging |
| 追踪/指标 | OpenTelemetry + Prometheus（go-zero 内置 /metrics） | Sleuth / Zipkin |
| 序列化 | HTTP/JSON | -（协议不变，降低对接成本） |
| 部署 | Docker Compose（VM），Nginx 前置 | - |

服务间协议为 **HTTP/JSON**，服务契约以各服务自有的 **`.api` 文件**（goctl 输入，路由与类型的单一事实源）描述，CI 校验生成物与契约一致。**不引入 proto / zRPC 工具链**（理由见 §3.2）。若个别链路未来出现万级 QPS 的内部调用，可局部引入 zRPC，不影响整体架构。

### 3.2 服务框架：为什么是 go-zero

选 go-zero 的理由：

1. **治理护栏开箱即用**：超时、熔断（breaker）、过载保护（load shedding）、限流、指标暴露、优雅停机，20 个服务无需各自接线即有一致的保守默认值。v2.1 方案里这些靠 kit 自行封装并维护默认值，现在由框架承担。
2. **goctl 产能与结构强制**：`.api` 文件声明路由 → 生成 handler / logic / types 骨架。"20 个服务结构一致"的保障从"脚手架 + 评审"升级为工具链保证，团队约定的落地成本大幅下降。
3. **服务发现原生支持**：etcd 是 go-zero 的一等公民，Consul 有官方适配包（`zeromicro/consul`）——注册中心无论最终选哪个（§3.3）都有现成路径。
4. **社区与文档**：国内生态活跃、中文文档完善，团队上手成本低。

框架用法的自我约束（防止框架范式渗透过深）：

- 业务服务只用 **api 服务形态**；服务间调用维持 HTTP/JSON，**不引入 zRPC / proto 工具链**。对外协议不变（双轨切流、前端对接零影响）；proto 的收益只在内部高频链路，出现之前不付这个成本（与 v2.1 立场一致）。
- **kit 收缩为业务侧薄封装**（§5）：只做框架不覆盖的团队约定（错误体、日志字段、脚手架模板），不重复造框架已有的轮子。

Spring Cloud 其余能力在 Go 中的去向：

| Spring Cloud 能力 | 去向 | 承载者 |
|------------------|------|--------|
| starter-web + 内嵌容器 + Actuator | 保留 | go-zero rest + 内置 /metrics；/healthz /readyz 显式注册 |
| DI 容器 / 自动装配 | **删除** | svc.ServiceContext 显式装配（go-zero 标准形态） |
| Feign 声明式调用 | 保留（形式变化） | 各服务自写 client struct（AI 辅助生成，成本低） |
| Ribbon 客户端 LB | 简化保留 | client 侧实例缓存 + 轮询 + go-zero breaker |
| Hystrix / Resilience4j | 保留 | go-zero breaker / load shedding |
| Config Server / Bus | **删除**（Go 秒级重启改变"改配置必须热更新"的前提） | go-zero config（yaml + 环境变量） |
| Gateway | **自研** | gateway 服务（go-zero，§4） |
| Eureka / ZK 客户端 | 替换 | go-zero 服务发现（etcd 原生 / Consul 官方适配） |
| Sleuth | 标准件 | OpenTelemetry SDK |
| Security 过滤链 | 保留 | go-zero rest jwt 中间件（服务内兜底）+ 网关认证中间件（§4.2） |

**流式场景不构成约束**：AI 直连流量由网关内的 AI 模块代理，SSE 用标准库 ResponseWriter / Flusher 实现（go-zero rest handler 可直接操作 writer，见 §4.4）；业务服务为常规 CRUD；少量自有 agent 服务的流式处理在其自身内实现。

### 3.3 注册中心：待定（Consul vs etcd）
两个候选：

| 维度 | etcd | Consul |
|------|------|--------|
| go-zero 融合 | **原生一等公民**（goctl 生成的代码即用，零胶水） | 官方适配（`zeromicro/consul`），一行配置接入 |
| 健康检查 | TTL/lease 会话级 | **应用级**（直接打各服务 /readyz）+ TTL |
| 运维界面 | 无（依赖第三方工具） | 自带控制台、DNS 接口、KV 存储 |
| 部署形态 | 3 节点集群，docker compose | 3 台独立 VM 跑 server + 每业务 VM 一个 agent |

（ZooKeeper 不适合作为 Go 栈注册中心的结论不变：无应用级健康检查、摘除延迟受会话超时约束、watch 一次性触发需自行补偿、运维重、无控制台。）

**两处接入点均做成可切换抽象**：

- 业务服务：注册与发现走 go-zero 的发现机制，etcd 与 Consul 的差异在配置层面；
- 网关：实例 watch 由网关自己的 discovery 适配层实现（etcd watch / Consul blocking query 各一个实现，接口相同）。

选型在实施阶段 0（§10）定稿后只改配置与适配层实现，不动架构。

**ZooKeeper 的处置**：Java 栈继续使用直至下线，期间零改动；Java 下线后 ZK 集群整体退役。双轨期 ZK 与新注册中心并存且零交互。

## 4. 网关层设计（自研 go-zero 网关）

### 4.1 职责边界：基础设施进网关，业务语义不进

**网关是 `services/gateway`**：一个 go-zero api 服务，Go 栈流量唯一入口，双实例部署。职责：

- **路由与转发**：`/api/v1/<service>/*` 按服务名路由，转发内核用标准库 `httputil.ReverseProxy`（不自己写代理循环）；
- **实例级 LB + 健康摘除**：注册中心 watch 维护实例表，实例掉线自动摘除；
- **认证验证**：JWT / API key 中间件（§4.2）；
- **请求级限流**：Redis 全局计数（多实例一致），不再受开源网关单实例内存态限流的限制；
- **trace 注入**：`X-Request-ID` 全链贯穿。

**鉴权为两级授权模型**：

- **网关：认证 + 粗粒度授权**。认证验证（JWT 签名/过期、API key 有效性）与**路由级权限判断**（"这个角色能访问这个 path 吗"、"这个 API key 的 scope 覆盖该路由吗"）在网关统一判定——依据 token claims 与声明式规则表（路径 × 角色/scope），无权限请求尽早 403，不打到业务服务，401/403 判定口径全站统一。约束：网关只读 claims 与规则表，**不调用业务服务查数据**——一旦某条判断需要反查业务数据，它就是细粒度授权，归服务层。
- **业务服务：细粒度资源级授权**。资源归属（"订单 123 属于用户 X 吗"）、租户数据隔离、业务状态判断——需要查业务库，只发生在持有该数据的服务内。
- **权限模型已定稿**（`permission-design.md`）：ReBAC 模式，OpenFGA 引擎以 Go module 嵌入 `services/authz`。两级授权的数据来源——粗粒度：authz 维护"平台角色 → 路由前缀"规则表并扁平化导出到 Redis，网关拉取后在本地内存判定，不实时回源；细粒度：业务服务经 kit client 调 authz 判定 API（Check 单点判定 / ListObjects 列表反向展开），Redis 缓存（键含模型版本号），**资源级判定 fail-closed**（引擎不可达且缓存未命中 → 拒绝）。

AI 能力（§4.4）虽"业务性"较强，但其迭代域是 provider 对接而非业务规则，且做成进程内可拆模块，边界明确。

| 职责 | 归属 | 理由 |
|------|------|------|
| 认证**验证** + **粗粒度授权**（路由级：claims × 声明式规则） | 网关中间件 | 一次判定全站生效；无权限请求尽早拒绝，语义统一 |
| **细粒度资源级授权**（归属、租户隔离、业务状态） | 业务服务 | 需要查业务库与领域规则，发生在持有数据的服务内 |
| 请求级限流 / 配额兜底 | 网关（Redis 全局） | 通用管控 |
| LLM 用量**计量**（token 计数归集） | 网关 AI 模块在链路上解析 usage 并上报（§4.4） | 计量随代理实现（数据来源闭环），出账规则是业务 |
| 计费**规则**（价目、套餐、账单） | 计费系统 | 纯业务 |
| 业务编排、agent 服务自身的断线语义 | agent 服务 / 业务服务 | 高频迭代的东西不进流量入口 |

### 4.2 认证：CAS + 两类调用方

平台有两类调用方，认证路径不同：

**人（浏览器，走 CAS）**：

1. 前端访问受保护页面 → 基座 302 到**已有 CAS 服务端** `/login?service=<回调地址>`；
2. CAS 完成认证后携带 ticket 重定向回前端回调页；
3. 前端把 ticket 提交给 authz 服务（8084）；
4. authz 服务调 CAS `serviceValidate` 校验 ticket、换取用户信息，映射/创建平台用户，向 authz 取用户平台角色写入 claims，**签发平台 JWT**；
5. 后续 API 调用带 `Authorization: Bearer <JWT>`，网关校验，服务链上透传生效；
6. 登出：清除平台会话并跳转 CAS 单点登出（SLO）。

**程序（AI agent、脚本、第三方系统，走 API key）**：没有浏览器交互过程，走 API key——authz 服务统一签发与管理，网关中间件校验（本地缓存 + TTL，不每次回源）。key 的 scope 为**路由前缀白名单**（签发时写入，网关本地比对，越界 403）；资源级调用以 key 的 owner（签发人）身份走正常判定——key 的实际能力 = scope 允许的路由 ∩ owner 的资源权限。key 管理规范（安全基线）：仅存 SHA-256 hash 不存明文、创建时一次性展示、支持过期/备注/吊销、记录 `last_used_at`。

**auth 与 authz 分立**：auth 管"你是谁"（CAS 对接、用户映射、JWT 与 API key 凭证生命周期）；authz 管"你能做什么"（组织树、平台角色、资源类型注册、共享授权、审计，内嵌 OpenFGA 判定引擎，提供 Check / ListObjects / `/me/permissions`）。故障半径分立：auth 宕机 = 全站无法登录；authz 宕机 = 权限变更停止、缓存未命中的资源级判定 fail-closed，路由级判定不受影响（网关规则表在本地内存）。完整设计见 `permission-design.md`。JWT 维持 HS256 全栈共享 secret（环境变量注入，经网关鉴权一次、服务链透传生效），服务内 jwt 中间件兜底校验。

### 4.3 按 path 的流量处理

```
Nginx ──► gateway（自研，go-zero，双实例）
            ├─ /api/v1/* ───► Go 业务服务 × 20（注册中心 watch + ReverseProxy，
            │                                    实例级 LB + 健康摘除）
            ├─ /llm/* ─────► 网关 AI 模块 internal/llm（进程内）──► 外部 LLM
            │                 provider 路由、故障转移、SSE 流式、
            │                 API key 注入、usage 计量、token 级配额（§4.4）
            ├─ /agent/* ───► 自有 agent 服务（普通反代；鉴权/计费/断线语义在服务内实现）
            └─ 认证：JWT / API key 中间件（§4.2）
```

超时模型：`/llm/*` 与 `/agent/*` 路由不套普通 API 的统一超时，改用空闲超时（idle timeout）+ 总时长上限，按路由声明。

### 4.4 AI 模块：网关内的 LLM 代理（`internal/llm`）


**形态**：`services/gateway/internal/llm/` 独立包，三个隔离要求：

- **配置独立**：provider 列表、模型映射、故障转移策略为本模块自己的 yaml（环境变量 + 文件，与全栈配置方式一致）；
- **依赖独立**：计量上报、配额 Redis 客户端等依赖只在本模块内；
- **可拆分边界**：模块不依赖网关其余内部结构（编译期保证不 import 网关其他 internal 包），对 handler 只暴露一个代理入口。若 AI 迭代节奏或流量特征与网关冲突（SSE 长连接堆积影响普通 API 容量模型、高频发版要求隔离重启），将该包平移为独立服务、网关改一条路由转发，无重写成本。

**合并的理由与代价（明记）**：

- 理由：组件最少——一个进程承担全部入口职能；网关是自有代码，没有 Traefik 时期"业务进不去"的约束；部署、监控、发布链路一条。
- 代价：AI 模块迭代 = 网关发版，存量 SSE 长连接会被切断（发布流程需处理连接排空，§7.2）；普通 API 与 LLM 流量共享容量模型。两者都由可拆分边界兜底。

**职责与实现要点**：

- **provider 路由与故障转移**：provider 列表、模型映射、故障转移策略为模块 yaml 配置；SSE 流式透传用标准库 ResponseWriter / Flusher 实现。
- **API key 管理**：平台持有的外部 LLM key 由本模块统一注入请求（上游客户端不接触真实 key），集中存储与轮换；按租户区分 key/配额的模型在 §4.6 PoC 中验证。
- **计量**：在链路上解析响应中的 usage（流式响应在最终 chunk 携带），异步上报计费系统出账；usage 缺失时按请求特征估算并标记。数据来源闭环——这是纯透传代理做不到的。
- **配额**：token 级实时配额由本模块实现（Redis 计数，多实例全局一致）；网关请求级限流仅作请求维度的粗粒度兜底。
- **设计参考 One API**（Go 开源，多 LLM provider 聚合网关）：其渠道管理 ≈ provider 路由 + 故障转移、令牌 ≈ key 分发、配额与用量统计的数据模型与本模块需求几乎重合，实现阶段以其为对照设计数据模型。

**边界**：不做 prompt 改写、内容审核等业务语义；若未来需要，作为模块的显式配置能力演进。

### 4.5 自研参考与开源方案分析（为什么不能直接用）

本项目对网关的四个硬性条件：**普通网关治理能力 + AI 网关能力 + Go 技术栈 + 无 K8s 部署**。逐一对照现有开源方案：

| 方案 | 不满足的条件 |
|------|-------------|
| Traefik | 开源版无 AI 网关能力（v2.1 已验证结论：provider 路由、token 级限流、计量均属商业版 Traefik Hub）；且本次决策为收敛组件，不再保留独立网关产品 |
| Skipper / Tyk（Go 网关） | 无 AI 能力。引入后仍需在其过滤器/插件体系内二次开发 AI 代理——等于多养一个网关组件，核心差异点（AI）还是要自己写，且二次开发受制于项目自身的范式与生态 |
| Higress / APISIX（ai-proxy） | AI 能力现成，但 Higress 以 K8s 为一等公民（standalone 为次级形态），APISIX 插件是 Lua 生态，与 Go 栈二次开发脱节；且均为重组件 |
| One API / LiteLLM（AI 聚合） | 只覆盖 LLM 聚合，无通用网关治理（路由、限流、认证的框架级能力）；面向个人/中小团队，多租户治理、审计、与自有 auth/计费系统的整合不满足；LiteLLM 为 Python，引入即多语言栈 |

**结论：没有现成产品同时满足四个条件，自研。** 工程量被两个事实压低：

1. 转发内核直接用标准库 `httputil.ReverseProxy`，不写代理循环；
2. AI 模块有 One API 的数据模型可对照（§4.4），需求清单已经过验证。

**自研时的参考实现**：

| 项目 | 参考什么 |
|------|---------|
| `httputil.ReverseProxy`（标准库） | 转发内核直接使用 |
| Traefik| 注册中心 watch、健康摘除、中间件链设计 |
| Skipper（Zalando） | 过滤器链抽象，生产级 Go 反向代理 |
| Tyk | 认证中间件（JWT / API key 多方式）与限流实现 |
| One API | AI 模块的数据模型：渠道 / 令牌 / 配额 / 用量 |



### 4.6 前置验证项（实施第一步执行）

AI 模块的关键行为在阶段 0 用 PoC 验证，结论落档后再进入阶段 1：

1. **流式行为**：SSE 首字延迟与吞吐（对照客户端直连外部 LLM 的基线）、客户端断连时的取消传播、超长空闲连接的处理。
2. **故障转移**：provider 故障时的切换语义（流式中途不可转移的放弃策略、非流式请求的重试边界）。
3. **计量覆盖率**：目标 provider 流式响应的 usage 字段实际行为（是否默认携带、如何开启）、缺失时的估算策略。
4. **key 注入与多租户**：按租户区分 key / 配额的实现方案验证。
5. **可拆分边界**：编译期校验 `internal/llm` 不 import 网关其余 internal 包，平移为独立服务的成本为零。

## 5. kit：公共约定模块（v2.2 收缩）


> 各服务团队的实际开发规范（目录骨架、API/错误码、跨服务调用、认证、配置、端口）见 `docs/backend-design.md`；本节只定义 kit 的定位与治理。

**收缩后的功能清单**：

| 包 | 职责 | 说明 |
|----|------|------|
| `errors` | 跨服务错误码约定、统一 JSON 错误体 | 框架不规定业务错误体格式，全栈统一格式（前端也依赖）由 kit 承担 |
| `logging` | 日志字段约定对齐、轮转初始化 | logx 能力框架已给，kit 只统一字段名（`service`/`trace_id` 等）、JSON 文件输出与轮转默认值（§9.2） |
| `template/` + 脚手架 | goctl 模板定制 | 生成物带本团队的目录骨架（repo/client 分层等，见 backend-design §2）与 kit 接线，保证服务结构一致 |


三个身份属性不变：

1. **编译期依赖，不是运行时组件**：不部署、无常驻进程，被编译进每个业务服务。
2. **约定的载体**：错误响应格式、日志字段等"20 个服务必须一致"的行为收敛于此。
3. **组合的成品**：任何成员可以完整读完。

负面清单：**不含业务逻辑、不出现业务名词**（user、order 等词汇出现在 kit 的 PR 中直接拒绝）；**不做运行时治理**；**不是强制依赖**（偏离约定需在评审中说明理由）。

## 6. 项目结构与边界规则（多人并行开发防冲突）

### 6.1 仓库结构（Monorepo + go workspace）

```
nemo/                            # 后端仓库（Go Monorepo，单仓多模块）
├── go.work                      # go workspace 统一管理所有模块
├── kit/                         # 公共层（§5，收缩后）
│   ├── go.mod
│   ├── errors/ logging/ template/
├── services/                    # 服务，每个一个 module
│   ├── gateway/                 # 自研网关（§4，含 internal/llm AI 模块）
│   ├── auth/                    # 认证服务：CAS 对接、JWT 签发、API key 管理（§4.2）
│   ├── authz/                   # 授权服务：组织/角色/共享/审计管理 + 判定 API，内嵌 OpenFGA 引擎（permission-design.md）
│   ├── user/                    # 业务服务 × 20
│   │   ├── user.api             # 契约：路由与类型的单一事实源（goctl 输入）
│   │   ├── main.go
│   │   ├── etc/user.yaml        # go-zero 配置
│   │   └── internal/            # handler / logic / svc / types / repo / client
│   ├── order/ ...
│   └── ...
└── deploy/                      # 部署资产
    ├── gateway/                 # 网关配置（路由、限流规则、provider 列表）
    ├── registry/                # 注册中心配置（Consul / etcd，定稿前两套并存）
    └── compose/                 # 各 VM 的 docker compose 编排
```


**为什么后端单仓（Go Monorepo，单仓多模块）**：核心前提是**后端单仓 ≠ 后端单体**。是"代码同仓管理，服务独立编译、独立部署、独立运行"，完全符合微服务的自治原则。理由：

1. **公共代码复用极致，从根源消除依赖版本冲突**（单仓相对分仓最核心的优势，也是减少冲突的关键）。公共能力收敛于 kit（§5）；单仓下所有服务直接 import 本地代码，版本天然一致；修改 kit 一次提交全仓生效，无需发版、无需各服务逐个升级依赖，彻底避免分仓模式下「公共 SDK 发版 → 20 个服务分别改版本 → 版本碎片化 → 兼容冲突」的恶性循环。

2. **Go 原生支持，工程化成本低**。Go 1.18 的 `go.work` 工作区机制就是为单仓多模块场景设计的：每个服务、kit 都是独立的 Go 模块（有自己的 go.mod），边界清晰，可独立编译、独立运行；本地开发自动引用本地代码，无需手动 replace；Go 编译速度快、增量编译能力强，20+ 个服务的构建性能压力可忽略。

3. **接口一致性强，跨服务协作冲突少**。统一控制台场景下，各服务的接口规范、权限模型、数据结构需要高度一致。单仓内统一维护接口规范、请求响应结构体约定、错误码，不会出现 A 服务分页用 `page/pageSize`、B 服务用 `offset/limit` 的碎片化问题；跨服务业务联动一次提交即可完成所有相关代码调整，不用跨多个仓库提 PR、对齐版本、同步发布。

按服务分仓为备选方案，仅在特定组织 / 合规场景下需要（服务归属完全独立的团队、无公共平台层、需要仓库级权限隔离）。

### 6.2 防冲突的五层机制（从硬到软）

1. **编译器强制（最硬）**：每个服务一个独立 go module，实现放 `internal/`。Go 编译器保证无法被其他模块 import。服务间禁止 import 彼此任何包，只能走 HTTP——由 CI 脚本用 `go list -deps` 校验，违规即红。
2. **仓库物理隔离**：共享代码收敛于 kit 单模块，禁止业务语义入库。各服务 go.mod 独立，服务 A 增删依赖物理上碰不到服务 B 的任何文件。
3. **契约归消费方**：跨服务调用的类型定义在调用方 `internal/client/` 内自建（只含自己需要的字段），**不建共享 model 包**。接口契约以各服务自有的 `.api` 文件描述（goctl 生成路由与 types，CI 校验 handler 实现与契约一致）；API 变更走版本化路径（`/v1/`）。
4. **目录所有权**：CODEOWNERS 按 `services/<name>/**` 划分 owner 审批权；kit 双 owner + RFC 流程。前端两个独立仓库按 `apps/<name>/**` 划分，owner 与后端对应服务保持一致（跨仓对齐，联动机制见 §8.5）。
5. **结构统一**：服务由 goctl（kit 定制模板）生成，结构完全一致（标准 go-zero 骨架 + repo/client 分层约定）。

### 6.3 依赖方向（单向，禁止环）

```
services/*  ──依赖──►  kit  ──依赖──►  第三方库
services/* 之间：仅 HTTP 调用，禁止 import
```

## 7. 部署方案（VM + Docker，无 K8s）

### 7.1 拓扑

```
    gateway ×2（VM-A/B，互为主备/轮询）
                   │
     ┌─────────────┼──────────────┐
     ▼             ▼              ▼
   VM-1          VM-2           VM-3
 (compose)     (compose)      (compose)
  user ×2       order ×2       agent-svc
  ...           ...            ...
  registry-agent registry-agent registry-agent

独立 VM：注册中心 server ×3（跨机房/机架；Consul 或 etcd，§3.3）
共享：MySQL / Redis / MQ（复用现有；MySQL 新增独立库 nemo_authz 作 OpenFGA 引擎存储，见 permission-design.md §8）
新增：Prometheus + Grafana（单 VM 起步）
```

- 每个 VM 一个 docker compose 文件（进 `deploy/compose/`，git 版本化），管本机全部业务容器 + 注册中心 agent。
- 网关与核心服务（auth、authz）至少双实例跨 VM 部署，单 VM 掉线不致全站不可用。
- 扩缩容 = 新 VM 上 compose up + 注册中心自动注册 + 网关 watch 自动感知，无需改网关配置。

### 7.2 发布流程（无 K8s，摘流量靠流程保证）

统一发布脚本（kit 仓库维护，全服务共用）：

1. 新版本容器启动，注册到注册中心（TTL 检查开始上报）
2. 健康检查通过 → `/readyz` 通过
3. 网关通过 watch 自动加入新实例
4. 旧实例：deregister → 等待摘除生效（LB/客户端缓存刷新，~10s）→ 验证无流量 → 停容器

优雅停机：服务收到 SIGTERM 后停止接收新请求（框架内置）、等待存量请求完成（上限 30s），然后退出。**网关发布特殊处理**：存量 SSE 长连接（`/llm/*`）要么等待排空（上限拉长，如 5 分钟）、要么主动断开并依赖客户端重连语义；自有 agent 服务同理自行处理流式连接的"排空或通知"策略。

## 8. 前端架构（两个独立控制台，各自微前端）

平台有**两个前端产品**，受众不同：**对内控制台**（团队自己使用）与**业务控制台**（业务同事使用）。两者基座架构相同，各自挂载不同的微应用集合与页面。每个产品采用云厂商控制台（阿里云、火山方舟）的标准形态：**一个入口 + 基座应用 + 业务微应用集群**，本质是前端领域的微服务化。按业务边界拆分、渐进式整合，不一次性全量重构。

> 各服务团队接入前端的具体开发规范（菜单注册、会话协议、HTTP 约定、跨应用事件、视觉规范）见 `docs/frontend-design.md`；本节只定义架构分层与拆分策略。

### 8.1 整体分层架构

从外到内分为四层，前后端职责清晰对齐：

| 层级 | 定位 | 核心作用 |
|---|---|---|
| 接入层 | 统一入口 | 统一域名、统一登录页、流量入口 |
| 前端层 | 基座 + 微应用集群 | 基座提供统一框架，微应用对应各后端服务的页面 |
| 网关层 | API 网关 + 微应用配置管理 | 统一 API 入口、鉴权路由（即 §4 的自研网关） |
| 服务层 | 各业务微服务 | 对应 20+ 后端业务服务，提供数据与能力 |

### 8.2 微前端架构与技术栈

**基座应用（主框架）**：每个前端产品一个"壳"，所有页面共享的部分全部收敛在这里：

- 全局布局：顶部导航、侧边菜单栏、面包屑、用户中心、全局搜索
- 统一认证：**CAS 登录流程**（跳 CAS → ticket 回调 → 换平台 JWT，§4.2）、登录态维护、Token 自动刷新、登出统一处理（含 CAS SLO）
- 权限管控：拉取用户权限列表，控制菜单显隐，向下透传权限数据
- 路由调度：根据 URL 路径加载 / 卸载对应业务微应用
- 公共能力：全局消息通知、埋点上报、错误监控、全局弹窗 / 遮罩
- 共享依赖：统一提供 Vue、Element Plus 等公共依赖，避免重复打包

**业务微应用**：对应各后端服务的页面，完全独立：

- 只负责自身业务域的页面逻辑、内部状态、子路由管理
- 遵循基座约定的生命周期（加载、挂载、卸载）和通信协议
- 独立开发、独立测试、独立部署，更新不影响基座和其他微应用
- 页面内容由各服务团队自行开发；同一服务可出现在一个或两个前端产品中

**技术栈**：基座与微应用统一采用 Vue 3 + TypeScript + Vite + Pinia + Element Plus。微前端运行时为 **wujie**（demo 已验证基座加载、大规模导航、页签多开、401 统一登出全链路；原 v2.1 待定项落定）。微前端在技术上允许微应用与基座技术栈不同，此能力仅作为未来整合遗留页面的**过渡手段**（异构是过渡态，终局收敛回同构）。

### 8.3 后端配套设计

前端能做到统一入口，依赖后端三层配套：

1. **API 网关**：所有前端请求统一打向网关，由网关根据路径转发到对应后端服务，同时负责统一鉴权、限流、日志审计，前端不用感知后端服务的具体地址。即 §4 的自研网关（JWT / API key 认证中间件）。
2. **统一身份与权限中心**：全平台共用一套用户体系、角色权限体系，前后端权限模型对齐，避免每个服务各自做登录鉴权。对应 Go 栈的 auth + authz 服务（认证与授权分立，§4.2；授权模型见 `permission-design.md`）。
3. **微应用配置管理**：管理所有微应用的静态资源地址、开关配置等，基座启动时拉取配置，实现微应用的动态加载和热更新。**范围限定于前端**：仅承载微应用注册信息与开关，不改变后端服务"无配置中心"的既定决策（后端配置仍为 yaml + 环境变量）；实现从简（静态配置文件或注册中心 KV 均可）。

### 8.4 拆分策略：按业务边界拆分，渐进式整合

拆分原则：

- **边界对齐后端**：原则上一个后端业务服务对应一个前端微应用，保持团队职责对齐（谁开发后端服务，谁维护对应前端微应用）。
- **公共能力上浮**：所有跨服务复用的能力（登录、导航、权限、组件）全部上浮到基座或公共库，微应用只保留纯业务逻辑。
- **独立可运行**：每个微应用既可以集成在基座里运行，也可以单独启动调试，不依赖基座。

落地三步法：

**第一步：先抽离基座应用**。搭建统一主框架，优先实现四个核心能力：统一布局与导航菜单、统一登录（CAS）与 Token 管理、路由分发（根据路径加载对应微应用）、基础公共组件与样式规范。

**第二步：改造现有页面为业务微应用**。不重写现有前端代码，少量改造接入基座：适配微前端框架的生命周期钩子（挂载、卸载）；移除自身的登录逻辑、顶部 / 侧边导航，改用基座提供的能力；内部路由加上统一前缀（如 `/user/xxx`、`/order/xxx`）。基座与微应用同域部署（静态资源统一经 Nginx 提供），无需跨域配置。

**第三步：统一路由与通信规范**。基座管理一级路由（`/user`、`/order`），微应用管理自身二级路由；通信通过全局状态 / 事件总线传递用户信息、权限数据，微应用之间不直接通信。

### 8.5 代码管理：前端两仓独立，后端一仓

**最终形态：后端 1 仓（`nemo`）+ 前端 2 仓（对内控制台、业务控制台各一仓）。**

两个前端产品受众与演进节奏不同（对内工具 vs 业务功能），独立成仓使各自的产品迭代互不牵制、仓库权限可按受众隔离；也避免一个仓同时承载两条产品线的全部微应用。

**每仓内部仍是 pnpm workspace Monorepo**（单仓多包）——"开发态统一管理提效，运行态独立拆分控险"在每个产品内部依然成立（公共包复用、统一构建/Lint/CI、跨服务联动一次 PR）。结构：

```
<console-repo>/                   # 对内控制台、业务控制台各一仓，结构相同
├── pnpm-workspace.yaml
├── apps/                         # 可部署的应用（独立构建、独立发布）
│   ├── console/                  # 基座：布局、登录（CAS）、权限、路由调度
│   ├── user/                     # 本产品线包含的业务微应用（每个后端服务一个）
│   ├── order/
│   └── ...
└── packages/                     # 被应用依赖的库
    ├── http/                     # 请求封装（错误码对齐 kit errors、X-Request-ID 注入）
    ├── shared/                   # 工具函数、微前端生命周期（defineMicroApp 等）
    └── ...
```

要点：

- **基座代码相同**：两个仓库的基座由同一套模板派生、各持一份副本，结构保持一致但可独立演进（受众不同，节奏可能分叉）。不做跨仓私有 npm 包——公共包当前量小，两仓各自维护；若未来碎片化严重再评估私有源（YAGNI）。
- **微应用产物复用**：微应用静态资源独立部署，基座经菜单注册表的 url 加载（frontend-design §3.2）——同一服务的微应用部署一份，可被两个控制台同时挂载（两仓注册表各登记一条），也可只出现在其中一个。
- **依赖规则**（ESLint + dependency-cruiser 强制）：apps 依赖 packages；packages 不依赖 apps；apps 之间禁止互相依赖（微应用间通信走基座的事件 / 全局状态协议）。基座放 `apps/`——基座是可部署的应用，不是被共享的库。

前后端分仓的代价与对冲：联动改动跨仓提 PR，存在时间差中间态。由既定的**契约向后兼容纪律**对冲（API 变更不破坏旧调用方，破坏性变更走版本化路径）：先发后端（新契约兼容旧前端）、再发前端，中间态无害。各仓 CODEOWNERS 按同一业务域对齐 owner（后端 `services/<name>` 对应前端仓 `apps/<name>`）；涉及契约变更的后端 PR 在描述中标注前端联动方。

### 8.6 与后端架构的衔接

- **请求层**：统一 HTTP client 封装于各仓 `packages/http`，baseURL 走 `/api/v1/*` 由自研网关路由；错误码对齐 kit `errors` 约定；client 自动注入 `X-Request-ID`，与后端日志的 trace_id 贯通（§9.2）。
- **认证**：登录走 CAS（§4.2），基座管理 token 生命周期；微应用经 props 接收会话信息，不自行登录。
- **双轨期**：后端 Java→Go 按 path 切流对前端透明（协议与 path 不变）；新页面一律对接 Go 入口的 path。
- **发布**：前端产物（基座、各微应用的静态资源）按版本发布并记录于发布清单，与后端镜像同套发布流程（§7.2）；基座与微应用相互独立发布。

## 9. 可观测性

### 9.1 指标与追踪

- 指标：各服务 `/metrics`（go-zero 内置暴露，Prometheus 拉取），Grafana 看板按服务 + 全局两级。
- 追踪：OpenTelemetry，Jaeger（或现有 Zipkin 兼容后端）起步。

### 9.2 日志：输出到文件（已确认）

流水线：Go 服务（logx，kit 统一字段）→ 本地文件（容器卷挂载）→ 轮转归档。后续如需接入 ELK 等集中平台，Filebeat 直接 tail 日志文件即可，下列格式约定无需变更。

kit `logging` 包统一约定：

- **JSON lines 格式**：一行一个 JSON 对象，grep 友好、机器可解析；接入任何采集/分析系统（ELK、Loki）均零解析成本。
- **统一字段名**：`time` / `level` / `msg` / `service` / `trace_id` / `error`——按服务过滤、按 trace_id 串联跨服务链路才有统一口径。
- **单行约束**：错误信息与堆栈作为字段嵌入同一 JSON 对象（Go 天然单行），不需要多行拼接规则。
- **trace_id 跨栈一致**：从入口注入（`X-Request-ID`），Java 与 Go 两侧日志均携带——双轨期一个 id 串起两栈的完整链路，是切流排障的关键能力。

文件输出需自管的配套（原本由 stdout + Docker logging driver 免费提供，改文件后归 kit 与部署模板承担）：

- **轮转**：统一采用进程内轮转（lumberjack 库，kit `logging` 内置默认值：按大小切割 + 保留份数上限），不依赖宿主机 logrotate。
- **卷挂载**：容器内日志目录必须挂载 volume，约定进 `deploy/compose/` 模板，否则容器重启日志丢失。
- **磁盘水位**：轮转保留份数/总大小上限统一默认值，kit 下发；排障时按服务定位到对应 VM 的日志文件。

## 10. 迁移策略（双轨并行，直接下线）

双轨期 Java 栈冻结只修缺陷、保持全量回退能力；Go 栈独立建设并逐步承接流量；全量切流后观察一段稳定期，Java 体系整体下线。

| 阶段 | 内容 | 验收标志 |
|------|------|---------|
| **0. 基建就绪** | 搭 monorepo 骨架 + kit + 注册中心集群（**定稿 Consul/etcd**）+ 自研网关服务（含 JWT/API key 认证中间件）；**执行 §4.6 AI 模块 PoC 前置验证**；建 CI（依赖规则检查、契约校验、镜像构建） | 一个示例服务可注册、被网关代理、指标上 Grafana；AI 模块 PoC 结论落档 |
| **1. 网关先行** | 自研网关承接增量新接口（新需求一律走 Go 入口，Java 栈开始冻结）；AI 模块上线，首个 agent 场景（LLM 直连）打通 | agent 链路生产可用，验证团队 Go 能力 |
| **2. 双轨并行建设** | Go 栈按服务逐个重建（1:1 平移，直接接管现有库）；Nginx 按 path 将已重建能力从 Java 入口切到 Go 入口，可按 path 灰度。个别未重建的下游能力经 Java 入口 VIP 临时调用（过渡态，随切流归零） | Go 入口承接的 path 比例逐步升至全量 |
| **3. 全量切流 + 观察期** | 全部流量走 Go 入口；Java 栈保留空跑作为回退预案，持续 1~2 个月，观察错误率/延迟/资源指标 | 观察期内无回退事件、无未覆盖路径 |
| **4. Java 直接下线** | 关停全部 Java 进程，退役 Spring Cloud GW 与 ZooKeeper 集群 | ZK 下线，Java 资源释放 |

风险与对策：

- **回退能力**：切流动作全部收敛在 Nginx path 规则，回退 = 切回 Java 入口，分钟级完成；观察期内 Java 栈不下线。
- **数据一致性**：同一时刻一条路径只由一个栈承载（path 级分流），无双写、无数据迁移。
- **切流验收关卡**：契约回放测试（录制现网请求响应、对新 Go 服务回放比对）+ 灰度期间对比 Java/Go 双侧错误率与延迟指标。
- **团队 Go 能力**：团队整体 Go 能力较强；阶段 1 以网关与示例服务练兵；Java 栈冻结释放人力投入 Go 栈建设。
