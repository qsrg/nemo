# 前端开发规范（基座 + 微应用）

面向各服务团队的前端接入指南。架构分层与拆分策略见 `architecture.md` §8，本文回答"我的服务要接进控制台，怎么写、怎么调、怎么发"。

> **迁移说明（v2.2）**：前端为**两个独立仓库**——对内控制台（团队自用）与业务控制台（业务同事使用），结构相同、基座代码相同，各自挂载不同的微应用集合。现有 `console-frontend/` 将按此拆分（迁移在实施计划中处理）。下文规范对两个仓库同样适用。

形态对齐阿里云/火山方舟控制台：**首页全量菜单目录 + 左侧固定菜单 + 页签多开 + AI 助手入口**。demo 已验证：基座加载、30 服务规模导航、多开状态保留、401 统一登出、刷新恢复全链路。

## 1. 技术栈与仓内角色

统一技术栈：Vue 3 + TypeScript + Vite + Element Plus + vue-router + pinia + wujie（微前端）。前端不允许自选 UI 库或状态库。

每个控制台仓库（pnpm monorepo）结构：

| 目录 | 角色 | 谁来改 |
|---|---|---|
| `apps/console` | 基座：登录（CAS）、首页目录、左侧菜单、页签、路由、会话、AI 入口 | 前端平台组维护，业务团队不改 |
| `apps/<service>` | 微应用：每个后端服务一个应用 | 各服务团队 |
| `packages/http` | 统一 HTTP 封装（token、401、错误） | 前端平台组维护，业务团队不改 |
| `packages/shared` | 跨应用共享类型/常量/生命周期（`defineMicroApp`、`setupBaseNavigation`） | 改动需相关服务评审 |

基座代码在两个仓库中由同一套模板派生、各持一份副本，保持结构一致但可独立演进。

## 2. 基座与微应用的职责边界

基座负责，微应用**不做**的事：

- 登录/登出页面与会话管理（token 只存在基座）
- 侧边栏、顶栏、页签（微应用不自带任何导航 UI）
- 路由注册（基座按菜单注册表生成 `/{service}/...` 通配路由）

微应用负责：

- 业务页面与业务组件（自己内部的二级路由可以自由使用）
- 自己的菜单片段声明（见 §3.2）
- 经 `props` 接收会话与导航信息、经 `packages/http` 调接口

## 3. 菜单与导航（20+ 服务的核心问题）

### 3.1 导航模型

```
首页（全量菜单目录）——发现：按业务域浏览所有服务与页面
左侧菜单（固定）    ——直达：全量菜单按业务域分组常驻，不依赖收藏
页签栏            ——多开：打开过的页面常驻，状态保留
AI 助手（⌘K）     ——兜底：不知道在哪时，问一句直达
```

三级结构贯穿所有入口：**业务域 → 服务 → 页面菜单**。域只是展示分组，不影响路由；菜单由基座统一渲染，保证选中态、折叠行为、权限过滤全站一致。

### 3.2 菜单注册表

服务的菜单以数据形式声明（demo 在 `apps/console/src/menus.ts`；生产由各服务 manifest 声明、基座启动时聚合，并叠加后端权限过滤）：

```ts
{
  key: 'user',              // 服务标识 = 一级路由段 = wujie 应用名
  title: '用户中心',
  url: 'https://console.example.com/micro/user/',  // 微应用部署入口
  domain: '用户域',          // 业务域分组
  icon: 'User',             // Element Plus 图标名
  menus: [                  // 页面菜单，第一项为进入服务的默认页
    { title: '用户列表', path: '/user', icon: 'List' },
    { title: '实名审核', path: '/user/kyc', icon: 'Stamp' },
  ],
}
```

`MenuItem.icon` 缺省沿用服务图标。图标映射集中在 `serviceIcons.ts`（服务图标、域图标、域色彩编码三个注册表），注册表只存名字字符串。

**新增一个服务 = 注册表加一条记录**，路由/菜单/图标/色彩全部自动生成。

### 3.3 路由约定

- 一级路由段 = 服务 key：`/{service}/...`，基座通配路由只承担 URL 语义（直达/刷新/守卫），页面由常驻容器渲染
- 微应用内部页面路由在自己的 router 中管理，必须以 `/{service}` 为前缀
- 刷新/直达任意 `/{service}/{page}` URL 可恢复到对应页面：基座经 `props.entry` 下发入口路径，微应用启动时 `setupBaseNavigation(router)` 恢复（`@nemo/shared`）

**承载兼容模式（原生 iframe 直连）**：新版 Chrome 把 wujie 的 blob 空页沙箱 iframe 隔离为 opaque origin（`contentDocument = null`），微应用脚本无法注入、页面永久 loading。基座已切换为**无沙箱直连**：微应用以独立形态运行（hash 路由），服务标识经 URL query（`#/?service=<key>`）下发，页签多开与常驻容器架构不变；每个微应用的默认页为 `ServiceOverview`（`packages/shared`）——按服务标识渲染该服务的集群列表（服务 → 机房 → 集群，与基座态势数据同构）。两条配套要求：微应用 dev server 必须显式开启 CORS（`server.cors: { origin: '*' }`，放行 opaque origin 的模块加载）；props 会话注入与 bus 事件协议（§6）保留代码，待浏览器环境恢复沙箱能力后切回 wujie。

### 3.4 导航交互规范（已实现于基座）

**首页（工作台）**：信息架构为「平台态势 + 待关注 + 最近使用」，回答"平台怎么样 / 出了什么事 / 我去哪干活"。全量服务目录只在左侧菜单一处，首页不再重复；服务发现由菜单 + AI（⌘K）兜底。

- **平台态势（域健康带）**：每个业务域一枚卡片——域色图标（`domainIcon`）+ 状态点（正常/告警）+ 聚合的实例数与告警数（`tabular-nums`）+ **机房分布块**（一格一个机房：数量即部署广度，颜色即机房健康，悬停看机房名/实例数/告警明细），单击进入**域态势页**（`/domain/:domain`）。部署模型为生产多机房多集群：**域 → 服务 → 机房 → 集群**（核心服务 6 机房、其余 3 机房；集群规模随服务/机房差异大，如 Redis 机房 10 有 10 个集群、机房 15 有 20 个），实例数按集群 → 机房 → 域逐级聚合
- **域态势页（`/domain/:domain`）**：态势卡的下钻落点。页头为域级聚合（集群/实例/机房/告警）；服务区块**异常优先**——有未恢复告警的服务置顶并默认展开，健康服务默认收起；机房表展示集群数、实例数、状态与告警摘要，机房行可再下钻**集群明细**（集群名、实例、状态），告警精确挂到集群，单击进告警中心定位。数据在 `health.ts`（`CLUSTER_COUNTS` 服务×机房集群数，集群实例静态生成；与告警中心 `alerts.ts` 按 serviceKey/region/cluster 关联），阶段二整体替换为监控服务/CMDB 接口
- **待关注（告警本体）**：态势计数必须落到内容——只展示**未恢复**告警，每条含严重度徽标（严重/次要，左缘竖条同色）、服务图标与名、机房、一句话标题、开始时间；单击进入**告警中心**（`/alerts?focus=<id>`）并定位展开该条
- **告警中心（`/alerts`）**：基座本地页面。状态筛选（未恢复/已恢复/全部）+ 业务域下拉；行内展示严重度、服务、机房、状态徽标（告警中/已恢复）、开始时间与持续时长；点击行展开详情（触发条件含当前值与阈值、影响范围、处理建议）与「去处理」入口（跳对应服务页）。顶栏铃铛显示未恢复计数。静态数据在 `alerts.ts`（`ALERT_ITEMS`，机房告警数与态势 `ALARM_SNAPSHOT` 对应），阶段二同源接入
- **最近使用**：消费 `prefs.recents`（进入服务时自动记录、最多 6 个），单击直达服务默认页；无记录时显示引导文案

**左侧菜单**（阿里云形态，固定模式）：

- 汉堡开关位于**顶栏最左**（与品牌名相邻，展开时高亮），点击在顶栏下方展开/收起 232px 菜单面板并推挤内容区——不设常驻图标栏，收起时内容区全宽；服务块的**展开/收起箭头位于行尾右侧**（展开态朝上、收起态朝下）
- 面板内容 = 注册表全量菜单**固定渲染**：服务分组（域彩色图标块 + 加粗应用名 14px，可点击折叠/展开）+ 页面菜单项（13px，带小图标），服务平铺不按业务域分组（当前仅两套前端系统，域分组无必要；首页目录仍按域分组浏览）
- 当前服务规模小（两套前端系统、菜单共 10+ 个），固定全量展示即可，**不引入收藏/常用筛选**；服务规模上来后再演进为收藏 + 后端权限过滤
- 从首页点进服务页面时面板自动展开，保持位置感
- 当前页高亮按**最长前缀**匹配，且只高亮当前服务那一组

**系统设置**（`/settings`）：基座本地页面（不经过微应用），维护用户偏好并持久化到 localStorage。面板底部固定入口。当前提供「菜单偏好」：各服务在左侧面板中的默认展开/收起状态（`stores/prefs.ts`），面板折叠与设置页开关以 store 为单一数据源、双向即时同步。

**页签多开**：

- 每个打开的页面一个页签（可关闭、localStorage 持久化、刷新后恢复）
- 每个打开中的服务一个**常驻 wujie 容器**，页签切换 `v-show` 显隐——同时打开的微应用全部保持运行、状态不丢
- 关闭服务最后一个页签时调用 `destroyApp` 销毁沙箱释放内存；**右键页签**弹出菜单：关闭当前 / 关闭其他（保留右键目标页签，仅剩 1 个页签时禁用）/ 关闭全部（清空并回工作台），批量关闭同样销毁不再有页签服务的沙箱
- 微应用容器**串行挂载**：多个 wujie 应用并发 startApp 存在竞态（脚本不执行），基座用队列保证同一时刻只有一个应用在启动，上一个 `afterMount`（或 8s 超时兜底）后挂下一个

**页签高亮/命名**：按最长前缀取叶子菜单名；URL 与页签联动，任何页签可直达。

## 4. 会话与认证协议（CAS）

**登录流程**（架构 §4.2，全在基座，微应用不参与）：

1. 用户访问受保护页面 → 基座 302 到已有 CAS 服务端 `/login?service=<回调地址>`
2. CAS 认证完成后带 ticket 重定向回基座回调页
3. 基座把 ticket 提交给 authz 服务（8084，2026-09-21 起 auth 链路并入），authz 调 CAS `serviceValidate` 校验并签发平台 JWT
4. 基座保存 token，后续 API 调用带 `Authorization: Bearer <token>`

- token 存储、登出逻辑全在基座；**微应用自己不登录、不存 token**
- 登出：基座清平台会话后跳转 CAS 单点登出（SLO）
- 基座经 wujie `props` 向微应用下发 `{ token, userInfo, base, entry }`：`base` 为服务路由前缀（navigate 事件按它过滤），`entry` 为入口完整路径（刷新恢复用）
- 微应用 HTTP 收到 401 时，**不自行跳转**，向 wujie bus 上报统一事件：

  ```js
  window.$wujie?.bus.$emit('unauthorized')
  ```

  基座监听该事件统一登出并回 CAS 登录（`WujieHost.vue`）
- 会话恢复：基座刷新后持 token 调 `/api/v1/me` 恢复用户信息，失败即重新走 CAS 登录

## 5. HTTP 与后端接口约定

- 统一使用 `@nemo/http`（`packages/http`），禁止业务代码裸用 fetch/axios
- baseURL 用相对路径 `/api/v1`：开发经各 dev server 代理、生产经自研网关（架构 §4）同域转发，微应用**不感知**后端各服务端口
- 自动附加 `Authorization: Bearer <token>`（token 由基座 props 注入）
- 错误约定：2xx 返回业务数据；4xx/5xx 抛出携带 `{ code, message }` 的错误，业务代码 try/catch 后用 ElMessage 提示

## 6. 跨应用事件协议

跨应用通信一律走 wujie bus，事件名进入本表统一管理，禁止口头约定：

| 事件 | 方向 | 载荷 | 语义 |
|---|---|---|---|
| `unauthorized` | 微应用 → 基座 | 无 | 会话失效，基座统一登出 |
| `navigate` | 基座 → 微应用 | `{string}` 完整路径 `/service/page` | 基座侧边栏/页签导航时广播；微应用按 `props.base` 前缀过滤后跳内部路由（memory 路由的桥接） |

微应用侧统一用 `@nemo/shared` 的 `setupBaseNavigation(router)` 接入（main.ts 一行），禁止自行监听 bus。

> 直连承载模式下（§3.3）bus 不存在，上述两事件暂不生效；协议保留，切回沙箱模式即恢复。

新增事件的流程：在本表登记 → 基座或对端微应用实现监听 → 联调。典型未来事件：`refresh-permission`（权限变更广播）。

## 7. 视觉与组件规范

- **Element Plus 就是控制台的设计系统**：不引入第二套 UI 库；颜色/间距一律用语义变量（`--el-color-primary`、`--el-border-color-light` 等），不写裸色值
- **深海青主色**：`#0e6e7e`，经 Element Plus 语义变量覆盖。基座注入 `:root`；**每个微应用必须在 `App.vue` 注入同一组令牌**（挂在应用根容器选择器上）——wujie shadow DOM 不继承基座变量，不注入则微应用回落 Element 默认蓝，造成全站色彩不一致
- **域色彩编码**：每个业务域一组 `{前景色, 浅底色}`（`DOMAIN_COLORS`，未登记的域自动循环取色），用于服务图标的色块底色——不读文字也能按颜色定位到域
- 图标统一用 `@element-plus/icons-vue`，注册表化（`serviceIcons.ts`），同一层级不混用线框/填充风格；层级约定：应用名用彩色图标块，页面菜单项用灰色小图标
- 数字列等宽（`font-variant-numeric: tabular-nums`），金额/计数不跳动
- 根节点必须显式设置背景色（`--el-bg-color`），避免系统深色模式下 canvas 透黑
- 反馈约定：请求失败用 ElMessage.error 并带恢复动作文案；>300ms 的加载用表格 skeleton/loading，不用整页转圈

## 8. AI 助手

- 入口：顶栏「问 AI」按钮 + 全局快捷键 ⌘K/Ctrl+K，**侧滑抽屉**形态——不离开当前页面，回答可带当前上下文；不做全屏对话首页（控制台高频动作是"进服务干活"，对话框是发现/导航工具，不是目的地）
- 会话状态在基座 pinia store（`stores/ai.ts`），首页 hero 输入框等入口经 store 打开
- 演示阶段回复为本地模拟流式；生产接**网关 AI 模块**（架构 §4.4）SSE 流式
- 演进路线：AI 回答嵌"页面跳转卡片"（AI 即导航层）→ 各服务 `.api` 契约转 function calling 工具（AI 跨服务查数）→ 写操作只允许"AI 预填表单 + 人确认"，AI 不直接执行高危操作
